# Fable 디자인 브리프 — 메인 화면을 "한 편의 글처럼 짜인 면"으로 (현재 구조 일부 유지)

새 Claude Code 세션의 Fable에게 이 문서를 그대로 보낸다.
작성: 2026-09-23. 사용자가 방향을 직접 선택했고, 측정값은 선행 세션이 실제로 실행해 얻은 것이다.

## 0. 너의 역할

너는 **디자이너이자 지휘자**다. 전체를 다시 디자인해도 좋다는 권한을 받았다.

다만 순서가 있다: **읽기 → 디자인 제안 → 사용자 승인 → 구현 → 검증**.
**승인 전에 코드를 갈아엎지 마라.** 이번 변경은 기존 2D 지도를 버리는 결정이라 되돌리기 어려운 범위가 크다.

최종 보고는 **한국어**로 한다.

## 2. 사용자가 선택한 방향 (확정)

사용자의 말 그대로: *"메인 페이지는 여러 문서들의 텍스트가 혼재되어 있는데(말이 되며 서로가 서로를 이어지게 하고 그런거) 완전 깔끔한 텍스트인데."*

사용자가 세 안 중 **"한 편의 글처럼 짜인 면"** 을 골랐다. 선택한 안의 설명:

> 여러 문서의 문단이 하나의 연속된 글로 짜인다. 카드도 칸도 없고, 문단 사이가 바뀌는 것이 곧 문서가 바뀌는 지점. 출처는 역여지에 조용히.

사용자가 고른 예시:

```
우주의 전체 크기는 현재 알 수 없다. 관측 가능한 지름은
약 920억~930억 광년이며—
            이 수치는 앞서 기록된 500m 주장을 정정한
            것이다. 이전 기록은 남아 있다.
빛이 이동하는 동안 공간 자체가 팽창했기 때문이다.

— 한 편의 글로 읽히고, 들여쓰기가 문서가 바뀌었다는 유일한 표시
```

### 사용자의 추가 지시 — 전부 갈아엎는 게 아니다

방향을 고른 직후 사용자가 덧붙였다: **"인데, 지금의 구조도 약간 유지하면 좋을듯."**

그러니 이건 **백지에서 다시 그리는 게 아니라, 짜인 글을 주된 읽기 면으로 삼으면서 현재 구조를 일부 남기는 일**이다. 무엇을 남기고 무엇을 바꿀지는 **네가 제안하고 사용자가 승인한다.** 혼자 결정해서 지우지 마라.

현재 구조 중 **이미 검증됐고 함부로 버리면 손해인 것들**:

- **관계 기반 배치** (`layoutEdges`/`layoutNodes` in `src/lib/spatial-data.ts`). 선언된 관계가 있으면 그 술어가 뜻하는 쪽 칸에 놓고, 없으면 나선으로 떨어뜨린다. §3-2(거짓 인접 금지)를 이미 만족하는 유일한 장치다. **짜인 글에서도 "무엇을 무엇 옆에 둘지"는 결국 이 로직이 답해야 한다.** 표현만 바뀌고 근거는 그대로 쓸 수 있다.
- **배치 근거 공개**: 하단 dock이 "최근순 배치 · 관계 1개 반영"처럼 왜 이렇게 놓였는지 밝힌다. 이 정직함은 반드시 유지해라.
- **단일 클릭 = 선택, 더블클릭 = 열기**, 드래그·관성, 빈 검색어 = 홈(홈 버튼 없음), 2초 유휴 후 검색창 복귀.
- **liquid glass dock/검색창**, 자체 호스팅 폰트, 불투명 리더 배경.
- 리더의 좌우 관계 컬럼(좌: 근거·상위 맥락, 우: 파생·정정) — 방향 의미론이 `relationSide`와 일치한다.

**함정**: 드래그를 남긴다면 `setPointerCapture`를 `pointerdown`에서 호출하지 마라. 포인터 캡처가 `pointerup`/`mouseup`/`click`을 재지정해서 클릭이 아예 동작하지 않게 된다. 현재는 `DRAG_THRESHOLD`를 넘는 첫 `pointermove`에서만 캡처한다. 자세한 건 `docs/SPATIAL_UI_HANDOFF.md`에 있다.

### 이 아이디어의 정체와 선행 연구

이건 새 아이디어가 아니라 **사용자 자신의 §2-10 "덩어리 정보"를 사람용 화면으로 옮긴 것**이다. `ORIGINAL_INTENT.md` §2-10 원문: *"문서글을 에이전트가 읽는게 아니라 유기적으로 어떤 덩어리 정보(여러 문서가 뭉쳐진)를 인식하는 그런걸 원하긴 함."* 지금까지 데이터 원칙으로만 있었고 UI로 표현된 적이 없다.

기존 용어는 **트랜스클루전(transclusion)** — Ted Nelson이 *Literary Machines*(1980)에서 만든 말로, 문서를 링크로 가리키는 대신 다른 문서의 해당 부분을 제자리에 끌어와 함께 읽게 하는 것. Project Xanadu의 "parallel documents"가 여러 문서를 나란히 두고 연결을 보이게 하는 구상이었다. 직접 조사해서 무엇을 가져오고 무엇을 버릴지 판단해라. 그대로 베끼라는 뜻이 아니다.

## 3. 이 디자인의 진짜 위험 — 먼저 답해라

### 3-1. 짤 재료가 없다

운영 데이터 실측(2026-09-23):

| 항목 | 값 |
|---|---|
| 문서 | **5** |
| 관계 | **1** (`corrects` 하나) |
| 의미 주석 | **0** |
| 검토 | **0** |
| 근거 | 10 |

"서로가 서로를 이어지게" 하려면 관계가 필요한데 **관계가 1개뿐이다.** 실제로 짤 수 있는 건 정정 쌍 하나가 전부다. 나머지 3개 문서는 서로 아무 관계가 없다.

**그러므로 네가 답해야 할 첫 질문**: 문서 5개·관계 1개에서 이 디자인이 정직하게 보이는가? 5,000개·관계 20,000개에서도 무너지지 않는가? **양 극단에서 다 성립하는 안을 내라.** 데이터가 풍부하다고 가정한 디자인은 이 제품의 디자인이 아니다.

### 3-2. 인접이 거짓말을 하면 안 된다 — 이번 디자인 최대의 위험

이건 절대 타협하지 마라. 선행 세션이 지적한 문제다:

기존 배치는 좌표가 배열 인덱스의 나선이라 **근접성이 아무 의미도 없으면서 의미가 있는 것처럼** 보였다. 그래서 관계 기반 배치로 고치고, 상태줄에 "관계 1개 반영"이라고 근거를 밝히게 했다.

**짜인 글은 이 문제가 몇 배 심하다.** 두 문단이 한 편의 글처럼 이어져 있으면 독자는 무조건 "이 둘은 연결돼 있다"고 읽는다. 실제로 연결돼 있지 않다면 그 화면은 거짓말을 한다. 그리고 이 제품의 존재 이유가 **"근거가 실제로 주장을 뒷받침하지 않는 문제"** 를 고치는 것이다. 여기서 거짓 인접을 만들면 제품이 자기 목적을 배반한다.

`docs/SPATIAL_DATA_HANDOFF.md`도 "근접성/검색 순위를 논리적 관계로 취급하지 않는다"고 명시한다.

따라서:
- **선언된 관계가 있을 때만 이어 붙여라.** 없으면 잇지 마라.
- 이어 붙일 관계가 없으면 **그 사실이 화면에 보여야 한다.** "관계가 없어서 나란히 놓았을 뿐"임을 독자가 알 수 있어야 한다.
- 관계 종류(`supports`/`corrects`/`depends_on`/`derived_from`/`contradicts`…)마다 **짜이는 방식이 달라야** 한다. 정정과 지지가 똑같이 보이면 안 된다.
- 검색 결과 순위는 관계가 아니다. 순위로 이어 붙이지 마라.

### 3-3. 읽기 모드와의 관계

메인이 이미 읽히는 면이면, 별도 읽기 모드가 왜 필요한가? 합칠 것인가, 남길 것인가, 다른 것이 될 것인가. 답을 내라. (현재는 더블클릭으로 전문 리더가 열리고 좌우에 관계 문서가 놓인다.)

## 4. 이미 측정된 것 (다시 파헤치지 마라)

- **검색 4초대**: 운영 `POST /api/v2/search`가 7.73 / 3.94 / 4.10초. `GET /records?limit=20`은 0.8~2.4초. 여기에 1000ms 디바운스가 붙는다. 원인은 순차 RPC 3회 + 행마다 재귀 plpgsql 가시성 검사 + 읽기마다 스냅샷 INSERT. **이건 별도 백엔드 세션 몫이다. 네가 고치려 들지 마라.** 다만 **디자인은 이 지연을 전제로** 해야 한다 — 4초 동안 무엇을 보여줄지가 디자인 문제다.
- **검색 모드**: `keyword_only`, 임베딩 `disabled`, 인덱싱 0건. 의미 검색은 꺼져 있다.
- **폰트**: Pretendard Variable(2.06MB)과 Source Serif 4(latin/latin-ext 서브셋, 93KB)를 `public/fonts/`에 자체 호스팅. OFL 1.1, `THIRD_PARTY_NOTICES.md`에 기록. **Source Serif 4에는 한글 글리프가 없다** — 한글 본문은 `"Noto Serif KR", "Noto Serif CJK KR", "Nanum Myeongjo", AppleMyungjo, Batang` 순으로 떨어진다. 이 스택에 고딕(Apple SD Gothic Neo, Malgun Gothic)을 끼워 넣으면 한글이 고딕으로 렌더링된다. 실제로 한 번 그렇게 깨졌다가 고쳤다.
- **CSS 특정도 함정**: `.spatial-node > span { display: block }`(0,1,1)이 `.spatial-node-copy { display: -webkit-box }`(0,1,0)를 이겨서 `-webkit-line-clamp`가 한 번도 작동하지 않았다. 발췌문이 4줄이어야 하는데 8줄로 나와 노드가 겹쳤다. 자식 선택자로 특정도를 올려 고쳤다. **텍스트를 자르는 CSS를 쓸 때 이 함정을 다시 밟지 마라.**

## 5. 지켜야 할 제약

### 5-1. 제품 원칙 (사용자가 반복해서 요구한 것)
- **실제 서버 데이터만.** 목업/데모 문서 배열 금지. 정적 테스트가 `mockDocuments|demoDocuments|const documents = [`를 차단한다. **디자인 시안·스크린샷에도 지어낸 문서를 쓰지 마라** — 실제 5개로 보여줘라. 그게 초라해 보인다면 그건 디자인이 아니라 데이터 문제이고, 그 사실 자체를 보고해야 한다.
- **선·화살표·격자선 금지.** 연결은 배치와 타이포로만.
- **연결망/그래프 시각화 금지.** 사용자가 "복잡한 연결망 시각화가 반드시 필요하지는 않다"고 직접 적었다.
- `globals.css`에 **`gradient` 문자열 금지** — `tests/static/stage05-ui.test.mjs`가 `gradient|text-align: justify|position: sticky`를 차단한다. AI 슬롭 방지 가드다.
- **WebGL / Three.js / SVG displacement / 큰 blur 레이어 금지.** `backdrop-filter`는 작은 크롬에만.
- 과한 장식, 불필요한 영어 괄호, 호들갑스러운 문구 금지. *"진짜 공학도가 만든 신뢰 있는"* 디자인.
- 읽기는 세리프(명조), 탐색/UI는 산세리프(Pretendard).

### 5-2. 접근성·기본기 (디자인이 바뀌어도 유지)
- 키보드만으로 전체를 쓸 수 있어야 한다.
- `prefers-reduced-motion`을 존중한다.
- 모바일 375×812에서 가로 넘침이 없어야 한다.
- 포커스 가시성, 스크린리더용 구조(`aria-live` 상태 알림 등)를 유지한다.
- 로딩/실패/빈 상태를 각각 설계한다. 실패를 빈 상태로 위장하지 마라.

### 5-3. 건드리면 안 되는 것
- `src/server/service/auth.ts`의 credential prefix `nuanox_`와 HMAC 문자열 `nuanox-agent-v1\0`. 기존 credential이 전부 무효가 된다.
- 공개 API `/api/v2/*` 계약을 조용히 바꾸지 마라. 외부 에이전트가 쓰는 표면이다.
- DB 마이그레이션·스키마 변경은 **명시적 승인 + 롤백 절차** 없이 금지.
- append-only/버전 보존 의미를 UI 편의를 위해 약화시키지 마라.
- 새 런타임 의존성은 승인 사항. 현재 `next`, `react`, `react-dom`, `ogl`, `server-only`뿐이다. 이 절제를 존중해라.

### 5-4. 절대 하면 안 되는 것
- **사용자의 채팅 승인 없이 commit / push / 배포 금지.** 한 번의 승인은 그 한 번에만 유효하다. (참고: 이 프로젝트는 원격 git이 없고, `vercel --prod`만으로는 `morum.vercel.app` alias가 안 옮겨간다.)
- `git reset --hard`, force push, 브랜치 삭제 등 파괴적 git 금지. 기존 미커밋 변경을 덮어쓰지 마라.
- `.env.local`, `.env`, Supabase/Vercel 시크릿을 **읽거나 출력하거나 하드코딩하지 마라.** 존재 여부만 확인(`[ -n "$VAR" ]`).
- **하지 않은 검증을 했다고 쓰지 마라.** 테스트가 실패하면 출력 그대로 보고해라.
- **승인 전에 기존 explorer를 삭제하지 마라.**
- 서브에이전트에게 commit 권한을 주지 마라. dev 서버를 띄우게 하지 마라.
- 포트 3000을 다른 세션이 쓰고 있을 수 있다. 확인하고, 남의 서버를 죽이지 마라. (Next.js는 같은 폴더에 두 번째 dev 서버를 거부한다.)

## 6. 에이전트 운용

- **디자인 판단은 네가 직접 해라.** 쪼갤 수 있는 일이 아니다.
- 구현 단계에서만 **Sonnet 서브에이전트 2~3개**에 위임하고, **파일 소유권을 겹치지 않게** 나눠라. 서브에이전트는 이 대화 맥락을 하나도 상속받지 않으니 프롬프트에 전부 넣어라(경로·현재 코드·"done"의 정의·제약·실행할 검사·보고 형식).
- **서브에이전트 요약을 믿지 마라. 네가 직접 `git diff`를 읽어라.**
- 실브라우저 검증은 **네가** 해라(브라우저 창은 하나다).
- 구현 후 **fresh context 리뷰 서브에이전트** 1개를 띄우되, 프롬프트에 **"correctness와 명시된 요구사항 누락만 보고하고 스타일 취향은 보고하지 마라"** 를 반드시 넣어라. 안 넣으면 없는 문제를 만들어 과잉 엔지니어링으로 끌고 간다.
- **예산(Max 5x)**: 5시간 롤링 윈도우당 Claude Code 프롬프트 대략 50~200개. 병렬 서브에이전트는 1시간대에 윈도우를 태울 수 있다. 동시 3개를 넘기지 말고, 윈도우가 소진될 것 같으면 **중간 상태를 문서로 남기고 멈춰라.**

## 7. 산출물 순서

### 1단계 — 디자인 제안 (코드 수정 없음, 사용자 승인 필요)
- §3의 세 질문(재료 부족, 거짓 인접, 읽기 모드와의 관계)에 대한 답.
- 메인 화면의 구조: 무엇이 무엇 옆에 오는가, 그 근거는 무엇인가, 출처를 어떻게 조용히 보이는가, 문서 경계를 어떻게 표시하는가.
- 관계 종류별로 짜이는 방식이 어떻게 다른가.
- 로딩(4초)·빈 상태·관계 없음·검색 결과 상태의 설계.
- **무엇을 유지하고 무엇을 바꾸는가**, 각각의 근거와 대가. 사용자가 "지금 구조도 약간 유지"를 요청했으니 §2의 유지 후보 목록을 하나씩 짚고 유지/변경/폐기를 밝혀라. 폐기하려는 것은 왜 짜인 글과 양립할 수 없는지 설명해야 한다.
- **실제 5개 문서로 만든 정적 프로토타입 1개.** 저장소 밖 임시 파일로 만들고, 데이터는 운영 API에서 실제로 가져와 써라. 지어내지 마라.
- 명시적인 **범위 제외 목록**.

### 2단계 — 구현 (승인 후에만)
서브에이전트에 위임, 네가 diff 검토, 실브라우저 검증.

### 3단계 — 검증 (전부 통과해야 "됐다")
- `npm run typecheck`
- `npm run test:static` (현재 18/18 — 기존 단언이 새 디자인과 충돌하면 **지우지 말고** 왜 바꿔야 하는지 보고하고 승인을 받아라)
- `npm run build`
- 실브라우저 + 실제 Supabase 데이터: 데스크톱/모바일, 키보드만으로 조작, reduced-motion, 로딩·실패·빈 상태, 콘솔 에러 없음
- 주장이 아니라 **증거**(명령어와 출력, 스크린샷, 수치)를 제시해라.

## 8. 시작 방법

**plan mode로 시작해서 §1을 읽고 §3의 세 질문에 답하는 것부터 해라.** 코드를 건드리기 전에 1단계 제안을 사용자에게 내고 승인을 받아라.

읽는 중에 방향이 갈리는 지점이 나오면 혼자 정하지 말고 `AskUserQuestion`으로 사용자에게 물어라. 사용자는 "추상적이라 뭐라고 할지 모르겠다"고 했으니, **추상적인 질문을 던지지 말고 구체적인 선택지를 보여주고 고르게 해라.**
